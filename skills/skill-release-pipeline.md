# Skill: Release Pipeline

## Step 1 — One version source

```
version.json   →  build label, VPK name, LiveArea version, update feed
```

Melee's port does exactly this (`platforms/vita/version.json`, release 0.8.15,
`APP_VER` 00.93). One file, read by the build script, so metadata can never drift
from the artifact.

## Step 2 — One build script

```powershell
.\build.ps1 -Configuration Release -Jobs 8
```

- Release = `-O3 -DNDEBUG`, no `-g`, no logging, no debugger linkage
- Debug = `-Og -g3`, logging on, debugger optional
- separate build directories per configuration so objects cannot mix
- optional flags for diagnostics: render trace, shader-cache sealing, resolution
  scale, cache warm-from-device

Never hand-assemble a release. If it is not in the script, it did not happen.

## Step 3 — Package the cache

If your renderer compiles shaders at runtime, ship a trained cache inside the VPK.
First-run stutter is the number one complaint about every port that skipped this.

Training loop: build with compile on → play with a writable cache → pull the cache
file over FTP → validate every record → merge with the packaged cache → ship.

## Step 4 — Release metadata

| Item | Note |
|------|------|
| VPK | `name-<version>.vpk` |
| `param.sfo` | title ID, `APP_VER`, `ATTRIBUTE2=12` |
| LiveArea | `icon0.png`, `bg0.png`, `startup.png`, `template.xml` |
| changelog | what changed, what broke |
| requirements | firmware, plugins, data files the user must supply |
| known issues | honest list |

## Step 5 — Updates (optional but worthwhile)

Two paths:

1. **In-app updater** — query a manifest, compare versions, download the VPK,
   install on next launch. Signed manifests (Ed25519) prevent a hostile mirror from
   pushing code.
2. **LiveArea integration** — a plugin watches an ini shipped in `sce_sys` and
   surfaces the update through the system UI. Check for documented plugin
   incompatibilities before recommending it.

Signing pipeline shape (from Melee): `sign-manifest.py` + `public-key.hex` +
`head.bin` + a crypto implementation in the app. The private key never leaves the
build machine.

## Step 6 — CI

```
 push ──▶ build Release ──▶ produce VPK artifact
 tag/version bump ──▶ draft release with VPK + changelog
```

Reproducibility checklist:

- [ ] clean checkout builds without manual steps
- [ ] toolchain version pinned (VitaSDK GCC version matters)
- [ ] no absolute paths in the project files
- [ ] shaders and assets generated by the build, not by hand
- [ ] version string in the artifact matches the tag

## Step 7 — Legal pre-flight

- [ ] no game data in the repository or the release archive
- [ ] no keys, firmware, or retail binaries
- [ ] third-party notices present (MIT/GPL/zlib as applicable)
- [ ] README states "you need your own copy" and what the user must supply
- [ ] credits name the SDK projects, decompilation, and the original developers

## Step 8 — After shipping

- keep the `.elf` for every published build
- keep the exact toolchain used
- tag the commit that produced each release
- when a bug arrives, reproduce with the saved artifact, not with `main`

## Never

- never publish a build you cannot rebuild
- never ship diagnostics enabled
- never let the release archive contain anything derived from game data
- never bump the version without regenerating the update feed
